## Simple Summary

Introduce governance-activated strict ECDSA recovery: validate signature components, harden modular inversion, and reject recovered public keys at infinity. Upgraded nodes also enforce deployment-time signature admission and query rules and normalize block witness signatures. Historical execution and high-S compatibility are preserved.

## Abstract

`ALLOW_STRICT_ECDSA_VALIDATION` enables strict transaction consensus and TVM recovery from the block after its activating maintenance block. Independently, deployment requires 65–68 bytes at transaction ingress, relay HELLO, and auxiliary signature queries; ECDSA relay and query recovery become strict immediately. P2P block ingress retains only an independently copied 65-byte witness signature prefix.

Transaction signatures must never be silently truncated: their bytes are committed by the block's transaction Merkle root. Witness signatures are outside that commitment. Permissions depending on infinity recovery require migration, and a known preliminary block-ingress limitation remains.

## Motivation

This TIP addresses four issues in legacy ECDSA recovery while preserving historical execution and high-S compatibility:

- **Component bounds:** Signature components are not consistently checked at the recovery boundary, allowing invalid inputs to reach curve operations.
- **Unbounded encodings:** Trailing signature bytes consume bandwidth, memory, and storage without changing the recovered signer.
- **Modular-inversion robustness:** Recovery inverts attacker-controlled `r`, requiring resource behavior bounded by operand size.
- **Point-at-infinity recovery:** Legacy recovery can derive an address from infinity, which is not a valid recovered public key.

## Specification

### 1. Activation and scope

The target release is java-tron v4.8.3. The implementation uses governance code `100` and `VERSION_4_8_3` (block version `39`); activation requires governance approval.

- The parameter defaults to `0`. Governance may set it to `1` after the required block version passes, and cannot disable it through a subsequent proposal.
- If maintenance block `H` activates it, consensus and TVM use legacy rules in `H` and strict rules from `H+1`.
- Final consensus and TVM use the candidate branch's applicable activation and permission state. Historical replay preserves the original rules. A rollback to an unactivated branch restores legacy mode despite the one-way governance setting.
- Each operation, including asynchronous work, must retain a stable validation context through snapshots or coordinated execution.

The policies below apply on upgraded nodes. Preliminary block ingress has the limitation described under Backwards Compatibility.

| Path | Before activation, including H | H+1 onward |
| --- | --- | --- |
| Fresh RPC/P2P transaction admission | 65–68 bytes; legacy ECDSA recovery | 65–68 bytes; strict ECDSA recovery |
| Auxiliary signature queries | 65–68 bytes; strict ECDSA recovery | Same |
| Relay HELLO | 65–68 bytes; strict ECDSA recovery | Same |
| Transaction ECDSA consensus | Legacy rules, preserving original bytes | 65–68 bytes; strict recovery |
| P2P block witness | Normalize, then legacy recovery | Normalize, then strict recovery |
| TVM recovery | Legacy recovery | Strict recovery |

Admission rules must not be applied to transactions inside historical blocks. The target release supports ECDSA (ECKey) only. PBFT message-signature validation is unchanged.

### 2. Encoding and strict recovery

#### Component bounds

Let `n` be the secp256k1 group order:

```text
n = FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141
```

Every strict recovery entry must reject null signatures/components, a null or non-32-byte digest, `r` or `s` outside `[1, n)`, and normalized `recId` outside `[0, 3]` before curve operations or inversion. High-S remains accepted.

#### Signature encoding

Transaction and witness protobuf signatures encode unsigned big-endian components:

```text
r[32] || s[32] || recovery[1]
```

The accepted length is 65–68 bytes, inclusive, at admission/query/HELLO boundaries and in strict transaction and direct witness validation. Reject original lengths outside this range before conversion, Base64 encoding, scalar construction, recovery, or task submission. Recovery interprets the first 65 bytes; up to three trailing bytes are accepted for compatibility. Preserve all accepted transaction signature bytes. Before proposal activation, historical transaction and direct witness validation retain their legacy minimum-length behavior. P2P witness inputs first follow Section 3.

Transaction and witness wire aliases retain their existing mappings:

| Wire recovery byte | Compact header | recId |
| --- | --- | --- |
| `0..3` | `27..30` | `0..3` |
| `4..7` | `31..34` | `0..3` |
| `27..30` | `27..30` | `0..3` |
| `31..34` | `31..34` | `0..3` |

All other values are invalid in strict mode. Compact headers `31..34` are normalized by subtracting `4`, then `recId = header - 27`.

TVM retains narrower input rules before and after activation:

| Precompile | Accepted v | Normalization |
| --- | --- | --- |
| `ECRecover` | 32-byte word: 31 zero bytes followed by `27` or `28` | `recId = v - 27` |
| `ValidateMultiSign`, `BatchValidateSign` | Signature byte `0`, `1`, `27`, or `28` | Map `0/1` to `27/28`, then subtract `27` |

Each entry enforces its existing layout and recovery-value restrictions before shared recovery. Transaction/witness aliases must not broaden TVM acceptance.

#### Modular-inversion robustness

After component validation, construct candidate point `R`, reject invalid coordinates, and perform the existing subgroup check. For valid `r`, compute:

```text
rInv = r^-1 mod n
```

Strict recovery must use an inversion algorithm whose work is bounded by operand size. The planned java-tron reference path uses Bouncy Castle `BigIntegers.modOddInverse(n, r)`; the legacy path retains `BigInteger.modInverse`. Equivalent algorithms are permitted if they preserve the valid domain, mathematical results, and specified failure behavior. For every `r` in `[1, n)`, the inverse must match the legacy result and satisfy `r * rInv mod n = 1`.

#### Point-at-infinity recovery

Recover:

```text
Q = rInv * (sR - eG)
```

When `Q` is infinity, legacy recovery encodes it as `{0x00}` and hashes the empty public-key payload, deriving:

```text
41dcc703c0e500b653ca82273b7bfad8045d85a470
TW6a53SLU4vM4QJBnK2vWVx4cqTnDChS1m
```

That address has a valid format, but infinity is not a valid recovered public key. Strict recovery must reject infinity before public-key encoding, address derivation, or permission evaluation. Successful non-infinity recovery must match legacy results. Recovery must not mutate on-chain state; exception types and messages are implementation-specific.

### 3. Block witness normalization

Upon deployment, P2P block ingress, including historical synchronization, must:

1. Apply existing message/block-size limits to the original input.
2. Reject witness signatures shorter than 65 bytes; retain exactly 65 bytes unchanged.
3. For longer signatures, independently copy the first 65 bytes before conversion or recovery, without retaining the oversized backing buffer.
4. Validate the prefix under the applicable branch rules and witness permissions.
5. Store and forward the normalized representation, including any retained serialized message. API output of that stored representation must reflect the normalized bytes.

Normalization must preserve header `raw_data`, transactions, block ID, signed digest, and transaction Merkle root. It must not rewrite high-S values, recovery aliases, or transaction signatures. It does not bypass original size limits or establish validity.

Existing database records need no bulk rewrite or compulsory read-time normalization. Old and newly synchronized archives may therefore expose different full protobuf bytes for the same block ID. Direct strict validation accepts 65–68-byte signatures but rejects an unnormalized signature longer than 68 bytes; callers needing normalization must perform it explicitly.

### 4. TVM failure results

Strict infinity recovery returns the existing signature-validation failure result:

| Precompile | Result |
| --- | --- |
| `ECRecover` | Empty byte data |
| `ValidateMultiSign` | 32-byte zero word (`false`) |
| `BatchValidateSign` | Existing 32-byte result array, with only the failed signature's byte set to `0` |

Other batch results and the precompile call-success flag remain unchanged. This failure does not inherently revert the enclosing transaction. ABI errors, timeouts, energy accounting, and costs retain their existing semantics.

### 5. Admission, queries, and client handling

Fresh RPC/P2P admission requires 65–68 bytes for every supplied signature upon deployment. Subsequent ECDSA recovery follows governance mode. RPC length failures return `SIGERROR`; all other admission checks remain applicable.

P2P batches retain existing checks for duplicate transaction IDs, unsolicited transactions, and missing contracts. After those checks, validate every supplied signature's length before clearing requests or submitting transactions. Any signature outside 65–68 bytes rejects the entire `TransactionsMessage` and disconnects the sender with `BAD_TX`; no transaction from that batch is submitted for processing. Outstanding requests remain available to the existing disconnect-recovery flow.

If all batch checks pass, clear requests for the received transaction IDs, retain unrelated requests, and continue normal handling without truncating signatures. These admission rules apply upon deployment, independently of governance activation.

Relay HELLO requires 65–68 bytes and strict ECDSA recovery upon deployment.

`getTransactionSignWeight` and `getTransactionApprovedList` must:

1. Apply existing multi-contract rejection first, then the signature-count limit; both return `OTHER_ERROR`.
2. Check every supplied signature length. A signature outside the 65–68-byte range returns `SIGNATURE_FORMAT_ERROR` before hashing `raw_data`, conversion, recovery, or task submission.
3. Omit the transaction extension on early structural/count/length errors: do not compute txID, echo the oversized transaction, or rewrite its signatures.
4. Otherwise construct the unchanged transaction extension and perform existing contract, local-state permission, address, and weight checks. ECDSA recovery is strict regardless of governance state. With otherwise valid query context, recovery failure returns `COMPUTE_ADDRESS_ERROR`; later failures retain existing transaction-extension behavior.

An empty signature list retains existing behavior; a supplied zero-length signature is invalid. Query results describe the node's current permission state. Queries can reject a 65-byte signature that pre-activation legacy consensus accepts, and success does not certify broadcast or consensus validity.

Shared helpers must select strict query recovery and applicable-branch consensus recovery explicitly. Signing workflows adopting strict checks for existing signatures must document their deployment timing. SDKs must check the exact broadcast payload, never silently trim signatures, and never transfer query results between different signature encodings merely because their txIDs match.

### 6. Verification reuse

Reuse requires an explicitly positive result and unchanged dependencies:

- Recovery: digest, complete validated signature bytes, engine, entry-specific input rules, and recovery mode. Witness recovery uses the normalized prefix; original-input size checks remain separate.
- Authorization: additionally the applicable permission state, permission ID, threshold, key weights, and allowed operations.

Input changes, activation, branch switching, and permission updates must invalidate or version affected results, including pending, re-push, popped, and pushing queues. Late asynchronous results remain tied to their original immutable input and context and must not become reusable authorization under a different context. No particular cache or context-object design is required.

## Rationale

### Why transaction signatures cannot be truncated

Transaction identity and the block's transaction commitment hash different data:

```text
txID(T)       = H(serialize(T.raw_data))
MerkleLeaf(T) = H(serialize(T))
```

The latter includes signatures. Replacing a legacy-valid 68-byte signature with its 65-byte prefix preserves txID and the recovered signer, but changes the Merkle leaf and root. Keeping the original header then causes a `txTrieRoot` mismatch; updating that root changes `BlockHeader.raw_data`, block ID, and witness signing digest, so the original witness signature no longer authenticates the block.

Validators must therefore preserve transaction signature bytes during received-block validation, storage, forwarding, and replay. Strict consensus accepts up to three trailing bytes (65–68 bytes total) and rejects longer signatures rather than repairing them. Before inclusion, clients may explicitly construct a corrected payload and submit it for fresh checks.

Witness signatures lie outside both header `raw_data` and transaction Merkle data; copying their interpreted prefix preserves these commitments. Existing [transaction hashing](https://github.com/tronprotocol/java-tron/blob/b33eed89a6a424c498d4fb1b03ca2c86eddf4840/chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java#L578) and [block Merkle construction](https://github.com/tronprotocol/java-tron/blob/b33eed89a6a424c498d4fb1b03ca2c86eddf4840/chainbase/src/main/java/org/tron/core/capsule/BlockCapsule.java#L218) show this distinction.

### Recovery compatibility

The inclusive 65–68-byte range preserves existing transaction-client compatibility, including commonly observed 68-byte encodings. Strict recovery does not introduce an exact-65-byte restriction at activation. The additional bytes do not relax scalar bounds, recovery-value checks, modular-inversion requirements, or infinity rejection. TVM precompiles retain their existing ABI input layouts; this range does not redefine them.

Low-S signing remains recommended, but verification retains high-S and existing entry-specific recovery aliases. Component and subgroup checks cannot replace the final infinity check. Governance controls consensus changes; deployment-time policies protect network and query boundaries without changing historical execution.

## Backwards Compatibility

### Client migration

Wallets, SDKs, hardware signers, exchanges, and signing services may continue emitting 65–68-byte signatures before and after proposal activation. Canonical 65-byte output remains recommended. Inputs outside that range must be corrected before deployment of the enforcing release, rather than waiting for governance. Clients must also handle missing query transaction extensions on early errors and strict query/relay recovery before activation.

Downstream Java callers must adapt to removed signing, weight-query, and recovery helpers and rebuild. `TransactionCapsule.sign()` does not replace the permission checks previously provided by `addSign()`.

Activation clears queued verification results; revalidation may temporarily reduce transaction capacity from H+1.

The 65–68-byte admission range introduced in [PR #6782](https://github.com/tronprotocol/java-tron/pull/6782) is preserved. Upgraded nodes continue accepting and forwarding otherwise valid transactions with 66–68-byte signatures without truncation, including after activation. An out-of-range signature rejects the entire P2P batch and disconnects its sender; RPC length failures return `SIGERROR`. Before activation, block validation retains its legacy length behavior, including longer signatures; historical replay preserves the original bytes and rules afterward.

A [reported scan](https://github.com/tronprotocol/tips/issues/935#issuecomment-5792658228) of blocks 72,179,711–82,691,711 found overlength signatures in 18,978,360 of 3,633,093,120 transactions (0.5224%), predominantly 68 bytes. This is historical, contributor-reported evidence, not a current failure-rate forecast. Before deployment, publish recent measurements, affected/fixed client versions, notification dates, the migration window, enforcing versions, and readiness criteria.

### Permission migration and historical execution

Legacy infinity recovery can supply authorization weight assigned to `TW6a53SLU4vM4QJBnK2vWVx4cqTnDChS1m` without a corresponding private key; authorization still depends on thresholds and other permission checks. Strict recovery removes that path. Permissions depending on its weight must migrate before activation. Without another usable permission or update path, affected accounts may be unable to initiate transactions or transfer assets, although they can receive funds. Query-dependent workflows are affected earlier, upon deployment.

The address itself remains usable through ordinary configured keys. The author's [September 30 check](https://github.com/tronprotocol/tips/issues/935#issuecomment-5914646449) found ordinary Owner/Active permissions. A contributor's [October 1 index scan](https://github.com/tronprotocol/tips/issues/935#issuecomment-5931040819) reported 3,250 infinity-signed outgoing transactions followed by ordinary signatures after the permission update at block 41,441,952. These dated observations require independent verification using original transaction bytes and historical permissions; they do not guarantee current permissions. Original pre-activation blocks must replay under legacy rules.

### Known preliminary block-ingress limitation

Preliminary witness validation depends on local Head state, which can differ from candidate-parent state and affect both acceptance and rejection. Normalization does not resolve this limitation. Activation readiness must account for it.

## Test Cases

Publish conformance results for the following coverage; this proposal does not claim completed validation. Tests should reference the rules above rather than redefine them.

| Area | Required coverage |
| --- | --- |
| Activation and state | H/H+1; historical replay; strict branch A → legacy branch B → A; permission differences and updates; pending/re-push/popped/pushing queues, local production, and late asynchronous completion |
| Input and recovery | Lengths 0/64/65/66/67/68/69/96, with 65–68 accepted and 64/69 rejected at bounded entry points; scalar boundaries 0/1/n−1/n/n+1; null components; digest lengths 0/31/32/33; all wire aliases, invalid recId, TVM-specific v rules, and high-S |
| Transaction commitments | Padded and trimmed transactions with equal txID but different Merkle leaves; unchanged header mismatch, changed-header signing digest; byte-preserving historical validation/storage/forwarding |
| Witness and networking | Independent-prefix copying, idempotence, original size limits, storage/forwarded/API bytes, old/new archive differences, direct strict acceptance of 65–68 bytes and rejection above 68 bytes, advertisement and synchronization; HELLO under both governance states |
| P2P transaction admission | Invalid lengths in first/middle/last transactions and multisign transactions reject the entire batch and disconnect the sender with `BAD_TX`; no normal or smart-contract task submission; requests retained for disconnect recovery; successful batches preserve 65–68-byte signatures and clear only received requests; existing batch-check precedence; both governance states |
| Queries and SDKs | Both governance modes; structural/count-error precedence; unsigned versus zero-length input; early extension omission without hashing/echoing; strict infinity recovery error with normal later response construction; local permissions; exact broadcast bytes and no cross-encoding certification |
| TVM | Legacy/strict results, ABI/energy/call-success preservation; multisign permission thresholds; valid/infinity/valid batch output beginning `01 00 01` in constant and worker execution |

Use a deterministic infinity vector `R = G`, `r = x(G)`, `s = 1`, `e = 1` for direct recovery. For `ValidateMultiSign`, construct the signature from its actual internally computed account/permission/data digest and configure the infinity key with weight and threshold 1, so rejection is attributable to recovery. Also compare successful recovery and `r * inverse(r) mod n = 1` across legacy, strict, independent conformant, and enabled native implementations.

Historical fixtures must independently verify original protobuf bytes and permission snapshots, including the reported [permission update at block 41,441,952](https://tronscan.org/#/transaction/dc65c4a470de05e142ba0c88e389ad441cea5333840c3d5480a7f80e8977bb90) and [ordinary control at block 41,476,026](https://tronscan.org/#/transaction/0b758f1a575638a456f82b9c45a24565ac5090559a5bd8d8ace52c384511c8d2). The control must authorize under recorded Active permission (`Permission_id=2`), recovering `TGxZme1LvLVqvPhbxF1en2kSsjeNGg6pNA` in both modes. Infinity fixtures must authorize under original legacy rules and fail strict recovery.

Publish versioned JSON vectors at an immutable commit with entry point, engine, mode, exact digest/signature/input bytes, required permission or VM state, and expected recovery, authorization, and call results. Historical vectors include provenance; SDK vectors include exact query responses and broadcast bytes. Fixtures must not depend on live permissions. Results must identify code version, environment, coverage, and incomplete runs; helper tests do not replace network/activation tests.
